# История входов (админка)

Раздел «Входы» в админке (`/sign-ins`) и блок «Входы» в карточке
пользователя: когда человек входил, с какого IP и из какого города, с какого
устройства, и откуда он пришёл к нам — с рекламы или с другого сайта.

## Что хранится

Таблица `sign_ins` (`packages/db/src/schema/auth/sign-in.ts`), строка на
каждую открытую сессию Better Auth: вход по коду или паролю, регистрация, вход
админа под пользователем (`impersonated_by`). Таблица `sessions` для истории не
годится: выход и истечение удаляют строку. Записью занимается хук
`session.create.after` в `initAuth` (`packages/auth/src/sign-in-log.ts`) —
для приложения и для админки одинаково. Сбой записи только логируется, вход он
не ломает.

Строки живут, пока жив пользователь (`ON DELETE CASCADE`). Срока хранения у
них нет: если он нужен, чистите `sign_ins` по `created_at` кроном.

## Откуда пришёл

Лендинг (`AdClick`, `apps/web/src/components/ad-click.tsx`) при каждом визите
пишет cookie на `.synoro.ru` на 90 дней — их видит и приложение:

- `ad_yclid` + `ad_yclid_at` — клик Яндекс Директа (`?yclid=`), как и раньше
  (`docs/direct.md`);
- `ad_visit` — строка вида `us=yandex&um=cpc&uc=psychologist&uu=…&ut=…&ref=…&lp=/…`:
  UTM-метки, сайт-источник (`ref`) и первая страница (`lp`).

Правила записи `ad_visit`: визит с `utm_*` или `yclid` — это реклама, он
всегда заменяет старое значение (последний рекламный клик). Любой другой визит
с внешним `document.referrer` сохраняется только если cookie ещё нет (первый
сайт-источник). Переход без referrer и внутренние переходы (с `*.synoro.ru`)
ничего не пишут. Отказ от аналитики в баннере cookie выключает всё это:
баннер стирает `ad_yclid*` и `ad_visit`, а сервер при входе не читает
источник у того, у кого стоит `cookie_consent=declined` (cookie общая для
`.synoro.ru`), даже если что-то осталось.

При входе `readVisitSource` (`packages/auth/src/visit-source.ts`) читает cookie
запроса, проверяет форму значений (cookie — пользовательский ввод) и кладёт
их в строку. Вид источника считается так (`sourceKind` в
`packages/api/src/routers/admin/sign-ins/source.ts`): есть `yclid` или
любая из меток `utm_*` — **реклама**; иначе есть сайт —
**переход с сайта**; иначе — **напрямую**.

Чтобы видеть конкретное объявление, ссылки Директа должны нести метки из
`docs/direct-campaigns.md` (`utm_campaign` — профиль кампании, `utm_content` —
`{ad_id}`, `utm_term` — `{keyword}`). Один `yclid` называет клик, но не
кампанию.

Ограничения: человек, который зашёл сразу в приложение, минуя лендинг,
cookie не получает — у него источник «напрямую». Если он пришёл с рекламы, а
вошёл через неделю, источник берётся из cookie на момент входа.

## Город по IP

IP приходит от Better Auth (`session.ipAddress`, заголовок `x-forwarded-for`).
Город ищет `lookupGeo` (`packages/auth/src/geo.ts`) в JSON-сервисе из
`GEOIP_URL` (по умолчанию `https://ipwho.is/{ip}?lang=ru`; понимает ответы
ipwho.is, ip-api.com и ipapi.co):

- **IP посетителей уходят этому сервису.** Упомяните его в политике
  конфиденциальности; чтобы выключить — `GEOIP_URL=` (пустая строка), тогда
  история хранит только IP.
- запрос идёт после ответа (`runInBackground`, таймаут 3 с), медленный сервис
  вход не задерживает; сбой логируется, город остаётся пустым;
- частные, loopback и link-local адреса сервису не отправляются;
- адрес, для которого город уже известен, повторно не запрашивается — берётся
  из прошлых входов;
- у бесплатных тарифов есть лимиты запросов — при росте входов смотрите
  логи `auth.geo_lookup_failed`.

## Админка

`admin.signIns.list` (`adminProcedure`): `query` ищет по имени, почте, IP и
городу; `userId` — один пользователь; `source` — `ad` / `referral` / `direct`.
Страница `/sign-ins` показывает те же фильтры ссылками (`?q=`, `?source=`,
`?page=`), карточка пользователя — его последние 20 входов со ссылкой на все
(`/sign-ins?userId=<id>`, точный фильтр, а не поиск по почте).
