# Напоминания и уведомления

Аналог Workflows из cal.com под нашу модель. Сейчас Synoro не пишет ни
клиенту, ни специалисту ничего о самой записи: из писем есть только ссылка
посетителю (`booking-link`), код входа, сброс пароля и приветствие. Неявки и
«я забыл» — главная потеря времени у специалиста, и это первое, что стоит
закрыть. Связанный документ — [регулярная запись](recurring-bookings.md):
каждое её занятие — обычная запись, напоминания работают и для неё.

## Что получает каждый

| Событие                         | Клиент / посетитель  | Специалист и администраторы | Тариф      |
| ------------------------------- | -------------------- | --------------------------- | ---------- |
| Запись создана                  | подтверждение        | «к вам записались»          | Бесплатный |
| Запись отменена                 | подтверждение отмены | «запись отменена»           | Бесплатный |
| За 24 ч до начала               | напоминание          | —                           | Бесплатный |
| За N ч до начала (второе)       | напоминание          | —                           | Про        |
| Расписание на завтра            | —                    | сводка вечером              | Бесплатный |
| В пакете осталось 1 / 0 занятий | «пополните» + оплата | —                           | Про        |
| После занятия                   | свой текст           | —                           | Про        |
| Клиент не записывался N дней    | свой текст + ссылка  | —                           | Про        |

Граница — по правилам `docs/pricing-strategy.md`: всё, что уменьшает неявки и
держит расписание в порядке, бесплатно; сообщения, которые приносят
специалисту деньги (пополнение пакета, возврат клиента) и свой текст —
«Про». Гейтинга тарифов ещё нет, поэтому до `billingStart` всё доступно
всем; проверку тарифа делаем одной функцией (`canUseCustomWorkflows`),
которая сейчас возвращает `true`.

**Гость** (бесплатная запись от администратора) аккаунта не имеет, поэтому
получает сообщения, только если в `guestContact` указана почта. Telegram-ник
не подходит: бот может написать только тому, кто сам его запустил. По одному
телефону напомнить нечем, пока нет SMS.

## Каналы

1. **Почта** — у клиентов и посетителей она есть всегда (`user.email`).
   Новые шаблоны в `packages/emails/emails/`: `booking-created`,
   `booking-cancelled`, `booking-reminder`, `staff-booking-created`,
   `staff-booking-cancelled`, `staff-daily-agenda`, `workflow-message`.
2. **Telegram** — один бот Synoro на всех. Отправка бесплатна, сообщения
   читают, в них работают кнопки. Главный канал для специалиста.
3. **SMS** — позже, только «Про» и с лимитом в месяц: каждое сообщение стоит
   денег. Провайдер (SMS.ru, SMSC, МТС Exolve) выбрать отдельно; тот же
   провайдер закроет «телефон не подтверждён» из `docs/guest-booking.md`.

Время в сообщениях — в часовом поясе практики с подписью пояса, если он не
московский: часовой пояс клиента мы не знаем.

**Конфиденциальность.** В тексте — только имя специалиста или название
практики, дата, время и ссылка. Никакого названия услуги вроде
«консультация психолога» на экране блокировки, никаких заметок к записи.

## Telegram: подключение

- Переменные окружения `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`,
  `TELEGRAM_WEBHOOK_SECRET` — в `packages/config/src/env.ts`, `runtimeEnv`,
  `.env.example`. Без токена Telegram просто выключен, как PostHog без ключа.
- Вебхук `apps/app/src/app/api/telegram/route.ts`: проверяет заголовок
  `X-Telegram-Bot-Api-Secret-Token`, разбирает `/start <код>` и нажатия
  кнопок (`callback_query`). Регистрация вебхука — скрипт
  `packages/jobs/src/scripts/telegram-webhook.ts` (`setWebhook` с
  `secret_token`), запускать при деплое.
- Привязка: в кабинете клиента, на странице `/b/<token>` после оплаты и в
  настройках специалиста кнопка «Получать напоминания в Telegram» ведёт на
  `https://t.me/<bot>?start=<код>`. Код — 32 случайных символа (лимит
  `start` — 64 символа `[A-Za-z0-9_-]`), в базе только SHA-256, живёт 15
  минут, одноразовый.
- Бот отвечает «Готово, напомню о записях к …» и сразу показывает ближайшую
  запись — так человек видит, что подключилось.
- `403 Forbidden: bot was blocked by the user` при отправке — помечаем чат
  отключённым и дальше шлём только почтой.

Привязку храним отдельной таблицей, а не колонкой в `user`: схему `user`
генерирует Better Auth (`bun auth:generate`).

## Модель данных

`packages/db/src/schema/notification/`:

```ts
// Чат пользователя с ботом.
TelegramChat {
  userId      text PK → user.id (cascade)
  chatId      text            // bigint из Telegram, храним строкой
  username    varchar(64)?
  linkedAt    timestamptz
  blockedAt   timestamptz?    // бот заблокирован — не отправляем
}

// Одноразовый код из ссылки t.me/<bot>?start=<код>.
TelegramLinkCode {
  codeHash    varchar(64) PK  // SHA-256, сам код не храним
  userId      text → user.id (cascade)
  expiresAt   timestamptz
}

// Настройки практики (одна строка на практику, создаётся лениво).
NotificationSettings {
  practiceId        uuid PK → practices.id (cascade)
  remindClient      boolean default true   // за 24 ч
  secondReminderMin integer?               // «Про»: за N минут, null — выкл.
  notifyStaff       boolean default true   // создана / отменена
  dailyAgenda       boolean default true   // сводка на завтра в 20:00
}

// Пользовательские правила («Про»).
Workflow {
  id          uuid PK
  practiceId  uuid → practices.id (cascade)
  trigger     enum: after_end | low_balance | inactive
  offsetMin   integer         // после окончания / дней без записи
  text        varchar(1000)   // с переменными {имя}, {дата}, {время}, {ссылка}
  active      boolean
}

// Журнал отправок: и очередь, и защита от повторов.
NotificationDelivery {
  id          uuid PK
  dedupeKey   text unique     // "reminder:24h:<bookingId>:<userId>:email"
  practiceId  uuid → practices.id (cascade)
  bookingId   uuid? → bookings.id (set null)
  userId      text? → user.id (set null)  // получатель
  channel     enum: email | telegram | sms
  template    text
  props       jsonb           // всё, что нужно для текста, без повторного чтения
  status      enum: pending | sent | skipped | failed
  attempts    smallint default 0
  sendAfter   timestamptz
  sentAt      timestamptz?
  error       text?
  createdAt   timestamptz
}
// индекс (status, sendAfter) для выборки очереди
```

`dedupeKey` + `insert … on conflict do nothing` — это и есть гарантия «не
больше одного напоминания»: cron может пройтись по одной записи дважды,
вебхук и страница оплаты — подтвердить одну оплату дважды, а сообщение
уйдёт один раз.

## Как отправляется

Тот же подход, что у `google-calendar-cleanup`: журнал в базе + задача
Hatchet по расписанию, а не отложенный запуск на каждую запись. Отложенные
запуски пришлось бы искать и отменять при каждой отмене и переносе; журнал
перепроверяет запись перед отправкой.

**Событийные сообщения** (создана, отменена, пополнение) ставятся там, где
событие происходит: `book`, `bookFree`, `cancel`, `cancelGuest`,
`settlePayment` вызывают `enqueueNotifications(db, event)` из нового
`packages/api/src/lib/notifications.ts`. Она пишет строки `pending` с
`sendAfter = now()` и, если Hatchet настроен, будит задачу
`deliver-notifications` через `runNoWait`, чтобы не ждать cron. Без Hatchet
отправляет сразу в процессе — как `dispatchEmail`. Ошибка отправки не роняет
запись: запись уже создана, строка останется `pending` для повтора.

**Напоминания** создаёт cron `notifications` (каждую минуту) в
`packages/jobs/src/workflows/notifications.ts`:

1. **Собрать.** Активные записи (`status = 'active'`, `hold_until is null`)
   с `starts_at` в окне `[now + offset − 10 мин, now + offset]`, у которых
   ещё нет строки с нужным `dedupeKey`, — вставить `pending`. Запись,
   созданная позже момента напоминания (записался за 3 часа), напоминание
   за 24 ч не получает: про неё клиент и так помнит.
2. **Отправить.** До 200 строк `pending` с `sendAfter <= now()` и
   `attempts < 5`, старые первыми. Перед отправкой напоминания
   перепроверить запись: отменена, перенесена (`starts_at` не совпадает с
   `props`) или снова в холде — `skipped`. Ошибка — `attempts + 1`,
   `sendAfter` сдвигается на `2^attempts` минут, после пятой — `failed` и
   строка в лог (`logger.warn("notifications.failed", …)`).
3. **Тихие часы.** Сообщения клиенту с 22:00 до 9:00 по времени практики
   переносятся на 9:00; исключение — напоминание за N часов, если иначе оно
   опоздает к записи. Специалисту «к вам записались» — в любое время,
   выключается в его настройках Telegram-бота.

`low_balance` срабатывает событием: `book` и `settlePayment` знают новый
баланс. `inactive` и `after_end` — тот же cron по своим окнам.

Без настроенного воркера напоминаний нет — так же, как сейчас нет очистки
Google Calendar. В проде воркер уже работает; в `docs/demo.md` дописать,
что для демо-стенда сообщения не уходят (демо-адреса), а журнал пишется.

## Telegram-кнопки

В напоминании клиенту — кнопки «Отменить запись» и «Открыть кабинет».
`callback_query` с `bookingId` проверяется в вебхуке: чат → `userId` →
участник практики → та же логика, что в `booking.cancel` (срок 24 ч,
возврат занятия). Чтобы не дублировать правила, вынести проверку прав и
срока из `routers/booking/cancel.ts` в `lib/bookings.ts`
(`cancelBookingAs(db, bookingId, userId)`), а процедура и вебхук вызывают
её. Перед отменой — подтверждение вторым нажатием («Точно отменить?»).

Ссылки в сообщениях: клиенту — `/bookings` (вход по коду), не `/b/<token>`:
токен посетителя хранится только хэшем, восстановить ссылку нечем.
Адреса — из `packages/api/src/lib/urls.ts`.

## Интерфейс

- **Настройки → Уведомления** (специалист): переключатели из
  `NotificationSettings`, подключение своего Telegram, для «Про» — второе
  напоминание и список правил `Workflow` с редактором текста и
  предпросмотром на последней записи.
- **Кабинет клиента** и `/b/<token>`: «Напоминать в Telegram» — одна
  кнопка, после подключения — «Telegram подключён · отключить».
- **Журнал** в карточке записи у специалиста: что и когда ушло («Напоминание
  отправлено в Telegram 14 нояб., 19:00»). Снимает вопрос «а клиенту точно
  напомнили?».

## Аналитика

Серверные события (`ServerEvent` в `packages/api/src/lib/analytics.ts`):
`telegram_linked`, `notification_sent` (`channel`, `template`),
`booking_cancelled_from_telegram`. Главная метрика эффекта — доля неявок
до и после: специалист отмечает их кнопкой «Клиент не пришёл»
(`booking.markNoShow`), и запись отменяется с `bookings.cancel_reason =
'no_show'` — отдельно от поздней отмены (`staff`) и отмены клиентом
(`client`).

## Порядок работ

1. **Почта и журнал**: таблицы `NotificationDelivery` и
   `NotificationSettings`, `enqueueNotifications`, задача
   `deliver-notifications`, cron с напоминанием за 24 ч, шаблоны «создана /
   отменена / напоминание» для клиента и специалиста. Уже даёт главный
   эффект.
2. **Telegram**: бот, привязка, канал в отправке, сводка на завтра для
   специалиста.
3. **Кнопки в Telegram** и вынос отмены в `cancelBookingAs`.
4. **«Про»**: второе напоминание, `Workflow` (низкий баланс со ссылкой на
   оплату, после занятия, неактивные клиенты), редактор текста.
5. **SMS** — когда выберем провайдера и посчитаем стоимость.

## Тесты

PGlite (`setupTestApi`), отправка подменяется фейковым транспортом:

- cron дважды подряд создаёт одно напоминание (`dedupeKey`);
- отменённая после постановки в очередь запись → `skipped`;
- холд без оплаты не получает напоминаний, оплаченный — получает;
- запись, созданная за 3 ч до начала, не получает напоминание за 24 ч;
- ошибка транспорта → повтор с увеличением `sendAfter`, после пятой —
  `failed`;
- отмена кнопкой в Telegram соблюдает срок 24 ч и возвращает занятие;
- чужой `callback_query` (чат другого пользователя) ничего не отменяет;
- тихие часы переносят сообщение на 9:00 по времени практики.
