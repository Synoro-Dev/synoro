# Биллинг «Про» через Точка Банк

Специалист платит Synoro за тариф «Про»: **149 ₽ за месяц** или **1490 ₽ за
год**, первые **14 дней** бесплатно. Деньги идут на расчётный счёт платформы
через интернет-эквайринг Точки — это не путь, которым клиенты платят
специалисту (тот идёт на его собственную ЮKassa / Т-Банк, `docs/guest-booking.md`).

## Как работает

- **Пробный период.** `practice.create` или первая оплата (что наступит раньше)
  вызывает `ensureSubscription`: строка `subscriptions` с
  `trial_ends_at = now() + 14 days`, один раз на
  пользователя. Других пробных периодов нет: проект запускается с пустой
  базой, а заполнение «ранних пользователей» в миграции `0006_billing` на
  ней ничего не делает.
- **«Про» включён**, пока `now()` раньше `trial_ends_at` или `paid_until`
  (`planOf` / `hasPro` в `packages/api/src/lib/billing`). Потом — бесплатный
  тариф, данные остаются.
- **Оплата.** «Настройки → Тариф» (`/settings/billing`) → `billing.checkout
  { period }` создаёт `subscription_payments` (pending) и платёжную ссылку
  Точки (`POST /acquiring/v1.0/payments_with_receipt`, карта +
  СБП, ссылка живёт сутки). Специалист возвращается на `/settings/billing?payment=<id>`,
  страница опрашивает `billing.status`.
- **Зачисление.** Банк — источник правды: `billing.status` и вебхук
  перечитывают операцию `GET /acquiring/v1.0/payments/{operationId}`.
  `APPROVED` с совпадающей суммой → `succeeded` и продление `paid_until` одним
  SQL-выражением с блокировкой строк (`settleSubscriptionPayment`): период
  начинается с конца текущего (пробного или оплаченного), а если «Про» уже
  закончился — с текущего момента. `EXPIRED` → `canceled`.
- **Автопродление — по желанию.** По умолчанию продление — новой оплатой.
  Специалист может при оплате поставить галочку «Продлевать автоматически»
  (согласие на списания, ссылка на Условия): тогда карта привязывается, и за
  сутки до конца оплаченного срока её списывает Cron — см. «Автопродление».

Закрыто на бесплатном тарифе: подключение ЮKassa / Т-Банка
(`payment.connect`), оплата пакетов клиентами (`payableAccount`: страница
записи прячет оплату, `checkout` / `reserve` отвечают `PAYMENTS_DISABLED`),
подключение своего домена (`domain.connect`) и приглашение администраторов
(`practice.addMember` с ролью admin). Уже подключённые домен и
администраторы продолжают работать.

## Настройка

1. Интернет-эквайринг в Точке подключён, торговая точка в статусе `REG`.
   Для чеков 54-ФЗ — онлайн-касса Точки.
2. Интернет-банк → Сервисы → Интеграции и API → **Создать JWT-ключ** с
   правами `MakeAcquiringOperation`, `ReadAcquiringData`, `ReadCustomerData`
   и `ManageWebhookData`. Сохраните `client_id` рядом с ключом.
3. `customerCode` — из `GET /uapi/open-banking/v1.0/customers` (объект с
   `customerType: "Business"`); `merchantId` (если торговых точек несколько) —
   из `GET /uapi/acquiring/v1.0/retailers?customerCode=…`.
4. Env (`packages/config/src/env.ts`):

   ```bash
   TOCHKA_API_TOKEN=<JWT>
   TOCHKA_CUSTOMER_CODE=<customerCode>
   TOCHKA_MERCHANT_ID=<merchantId>     # если торговых точек несколько
   TOCHKA_TAX_SYSTEM=usn_income        # обязательно для оплаты с чеком
   ```

5. Вебхук (один раз на ключ). Точка шлёт тестовое уведомление и не создаёт
   вебхук, если адрес не ответил 200 — деплой с маршрутом должен быть уже
   доступен по HTTPS. Из корня репозитория, с `TOCHKA_API_TOKEN` и `APP_URL`
   в `.env`:

   ```bash
   bun billing:webhook create <client_id>   # PUT, адрес — ${APP_URL}/api/billing/tochka
   bun billing:webhook show <client_id>     # что зарегистрировано
   bun billing:webhook test <client_id>     # тестовое уведомление на адрес
   bun billing:webhook delete <client_id>
   ```

   Другой адрес — третьим аргументом. В песочнице вебхуков нет.

   Тело вебхука — JWT (RS256). Подпись не проверяем: из него берём только
   `operationId` и перечитываем операцию по API своим ключом. Пока банк не
   подтвердил оплату, маршрут отвечает 503, и Точка повторяет (до 30 раз).
   Без вебхука оплата зачислится, когда специалист вернётся на страницу.

Без `TOCHKA_API_TOKEN` / `TOCHKA_CUSTOMER_CODE` / `TOCHKA_TAX_SYSTEM` пробный
период работает, а кнопки оплаты выключены. На демо-стенде (`DEMO_LOGIN_EMAIL` без Точки)
оплата «Про» проходит мгновенно, как платежи `demo-` магазинов.

## Песочница

[Официальная песочница Точки](https://developers.tochka.com/docs/tochka-api/pesochnica)
позволяет пройти оплату тарифа без денег, ключей и подключённого эквайринга:

```bash
TOCHKA_SANDBOX=true
```

Больше ничего задавать не нужно: `TOCHKA_API_TOKEN`, `_CUSTOMER_CODE`,
`_MERCHANT_ID`, `_API_URL` и `_TAX_SYSTEM` в этом режиме игнорируются.
Используются публичные тестовые значения — адрес
`https://enter.tochka.com/sandbox/v2`, токен `sandbox.jwt.token`,
`customerCode` `1234567ab`, `merchantId` `200000000001097`, налогообложение
`usn_income` (`SANDBOX` в `packages/api/src/lib/billing/tochka.ts`).

Что это даёт, а что нет — из-за устройства самой песочницы:

- **Ответы захардкожены**, а платёжная ссылка **не открывается**: оплатить
  в банке нельзя. Поэтому `billing.checkout` реально вызывает песочницу
  (проверяются адрес, токен, формат запроса и коды ошибок), но ответ банка
  не используется: `external_id` платежа — `sandbox-<id>` (иначе второй
  платёж упёрся бы в уникальный `operationId`), а вместо ссылки специалиста
  возвращают на `/settings/billing?payment=<id>`.
- **Оплату подтверждаете вы.** На этой странице у ожидающего платежа есть
  кнопки «Оплатить» и «Отказаться» — `billing.sandboxPay`. Дальше всё как с
  настоящим банком: тот же `settleSubscriptionPayment` продлевает `paid_until`,
  пишет историю оплат, открывает возможности «Про».
- Опрос банка (`billing.status`) и вебхук в этом режиме банк не спрашивают:
  он ничего не знает о наших платежах. Вебхук регистрировать не нужно.
- `sandboxPay` отвечает только за платежи с `sandbox-` в `external_id`, и
  только у их владельца. Реальный платёж, открытый до включения флага, им не
  закрыть.
- Страница тарифа показывает плашку «Тестовый режим».

Полный путь с настоящей оплатой картой или СБП проверяется только в боевой
среде, например платежом на 149 ₽ с собственной картой.

**Не включайте `TOCHKA_SANDBOX` там, где есть настоящие клиенты:** любой
пользователь сможет сам «оплатить» тариф. Стенд с `DEMO_LOGIN_EMAIL` без
Точки по-прежнему оплачивает мгновенно, но при `TOCHKA_SANDBOX` приоритет у
песочницы.

## Письма об окончании «Про»

Cron `pro-notices` (`packages/jobs/src/pro-notices.ts`) раз в час пишет
владельцу, когда кончается то, что включает «Про» — пробный период или
оплаченный срок, смотря что позже:

- **за 14 дней** — только когда кончается оплаченный год;
- **за 3 дня** и **в день окончания** (до двух суток после него — позже не
  пишем, чтобы первый запуск не разослал письма давно закончившимся).

Письма уходят с 9:00 до 21:00 по Москве. Каждое письмо захватывается в
`sent_notices` (конец периода — в ключе) на пять минут и отмечается
отправленным, когда передано в `send-email`: второй воркер его пропустит,
ошибка отправки снимает захват, а захват упавшего воркера истекает, и письмо
уйдёт при следующем запуске — но только пока открыто окно этого письма:
если период успел закончиться, «за 3 дня» уже не отправится, придёт
«закончился» (упавший сразу после отправки воркер может повторить письмо). После оплаты у периода новый конец, и отсчёт начинается заново.

**Без воркера Hatchet писем нет.** Сейчас воркер в k3s масштабирован в ноль
(`.github/workflows/deploy.yml`, шаг «Restart deployments»). Запустить его
с `HATCHET_CLIENT_TOKEN` нужно до открытия регистрации: письмо «за 3 дня»
первому пробному периоду уходит уже на 11-й день, а пропущенное окно не
наверстать — после окончания приходит только «закончился». Вместе с воркером
заработают `booking-reminders` и `google-calendar-cleanup`.

## Автопродление

**Как устроено.** Подписка Точки **без графика** (`recurring: true`): банк
хранит карту, а суммы и даты списаний определяем мы. Так цены берутся из
`PRO_PRICES` на момент списания, месяц и год — одна и та же подписка, а
списание можно перенести или пропустить, не трогая банк. Подписка с графиком
(`Options.trancheCount`) не подходит: у неё фиксированные сумма и число списаний,
а метод продления (`prolong`) Точка в документации не описывает («продлить
подписку пока нельзя»).

1. **Согласие.** `billing.checkout { period, autorenew: true }` — галочка с
   текстом согласия и ссылкой на Пользовательское соглашение на
   `/settings/billing`. Время согласия пишется в
   `subscription_payments.autorenew_consent_at`. Вместо `payments_with_receipt`
   вызывается `POST /acquiring/v1.0/subscriptions_with_receipt` с
   `recurring: true` (без `Options`, `ttl`, `paymentMode` и `saveCard`): ссылка
   принимает только карты и живёт 7 дней, на оплату после перехода — час.
2. **Первая оплата** — тот же путь, что у обычной (`billing.status`, вебхук,
   `settleSubscriptionPayment`): платёж на сумму выбранного периода. Одним
   SQL-выражением с продлением `paid_until` создаётся (или заменяется)
   строка `subscription_autorenewals`: `external_id` — `operationId` подписки,
   `period` — период, который будет списываться, `status = 'active'`.
3. **Списание.** Cron `billing-renewals` (`packages/jobs/src/billing-renewal.ts`,
   раз в час, в :30) берёт включённые автопродления, у которых `paid_until`
   наступает в ближайшие 24 часа (и ещё 3 суток после, если воркер стоял), и
   для каждого:
   - вставляет платёж `pending` с `charged_for = paid_until` — **до** обращения
     в банк, одним SQL-выражением с блокировкой строк, которое заново проверяет:
     автопродление всё ещё включено, подписка банка та же, `paid_until` не
     сдвинулся (ручная оплата), последняя попытка была не позже чем 12 часов
     назад. Так отмена или оплата, случившиеся после выборки, не приводят к
     списанию. Уникальный индекс `(user_id, charged_for)` не даёт ни второму
     воркеру, ни повтору workflow, ни упавшему после списания воркеру списать
     тот же период ещё раз;
   - вызывает `POST /acquiring/v1.0/subscriptions/{operationId}/charge`
     `{ Data: { amount } }` (сумма из `PRO_PRICES`, ₽) — ответ банка
     `{ Data: { result: true } }` считается подтверждением;
   - при `true` зачисляет платёж тем же `settleSubscriptionPayment`: новый
     период начинается с конца текущего (или с «сейчас», если «Про» успел
     закончиться), письмо «Про продлён»;
   - при `result: false` или 4xx (кроме 401/403/429) — отказ: платёж
     `canceled`, период освобождается для повтора, `failed_attempts + 1`, письмо
     «Не удалось продлить». Повтор не раньше чем через 12 часов; после **3-го**
     отказа автопродление отключается (`charge_failed`), письмо «Автопродление
     отключено»;
   - при 401/403/429 или без ключа — ничего не ушло: попытка забывается, время
     последней попытки возвращается, повтор на следующем часовом запуске, лог
     `billing.renewal_not_sent`;
   - при сетевой ошибке, 5xx/424 и нечитаемом ответе — **неизвестно, списали ли**:
     платёж остаётся `pending` с занятым периодом, повторного списания не будет,
     в лог пишется `billing.renewal_unconfirmed`. Разбирать руками: проверить в
     интернет-банке Точки, прошло ли списание; если да — зачислить платёж
     (`settleSubscriptionPayment`), если нет — удалить строку, и следующий запуск
     попробует снова.
   - Если банк списал, а запись не удалась, лог `billing.renewal_unrecorded`.
     В песочнице Точки, на демо-стенде (`demo-…`, `sandbox-…`) и без
     `TOCHKA_API_TOKEN` Cron ничего не списывает.
4. **Отмена.** `billing.cancelAutorenew` (кнопка «Отключить автопродление» на
   странице тарифа): `status = 'canceled'`, `cancel_reason = 'user'`; уже
   оплаченный период остаётся. Также автопродление отключают возврат
   (`billing.refund`, причина `refund`) и отказы банка (`charge_failed`).
   **Подписку без графика в банке отменить нельзя** (`status` меняется только у
   подписок с графиком), поэтому «отключено» значит «мы не списываем»; чтобы
   отозвать карту у банка, нужен интернет-банк. Новое согласие заменяет подписку
   (`external_id`) новой — но только если оно дано позже и текущего согласия, и
   последней отмены: запоздавшее подтверждение старой ссылки продлевает срок, а
   отмену и более новую карту не трогает.
5. **Письма.** `renewal-notice` (`packages/emails`): списано / не удалось /
   отключено — по одному на платёж (`sent_notices`, ключ `renewal:<paymentId>`).
   Письма рассылаются по платежам (`subscription_payments.decline_kind` у
   отказов, успешные списания — `charged_for`), а не по подпискам, которым пора
   платить, поэтому после сбоя отправки письмо уходит со следующих запусков
   (3 суток). `pro-notices` не пишет «заканчивается» тем, у кого
   оплаченный срок продлевается сам; «закончился» приходит, если не продлился.

**Возвраты платежей по подписке.** Точка возвращает их **только в
интернет-банке** (и первую оплату с согласием, и каждое списание). Поэтому
`billing.refund` для них отвечает `BANK_ONLY`, пока не передан
`recorded: true` («деньги уже возвращены в банке»): тогда процедура только
снимает период и отключает автопродление, банк не вызывается. Платежи без
подписки возвращаются как раньше — через API.

**Цены.** Сумма списания — `PRO_PRICES` на момент списания. Если поднять цену,
действующие автопродления начнут списывать новую без отдельного согласия — это
вопрос к Условиям (нужно предупреждение заранее).

**Проверка.** В песочнице Точки ответы захардкожены, платёжная ссылка не
открывается, а `charge` ничего не списывает: песочница не проверяет ни
привязку карты, ни списание. Весь путь — привязка карты, `charge`, отказ карты,
возврат — проверен только тестами со stub-ом банка (`autorenew.test.ts`) и
**должен быть проверен на боевом платеже**: подключить автопродление за 149 ₽
своей картой, сдвинуть `paid_until` в базе на ближайшие сутки и дождаться Cron.
Допущения, которых нет в Postman-коллекции Точки и публичной OpenAPI-схеме,
перечислены в описании PR.

## Возвраты

`billing.refund { paymentId }` (только администратор платформы): возвращает
платёж целиком через `POST /acquiring/v1.0/payments/{operationId}/refund`, а
затем одним SQL-выражением ставит `subscription_payments.refunded_at` и снимает
оплаченный период с `subscriptions.paid_until` (если период начинался не
позже конца пробного, `paid_until` становится `null`). Статус платежа остаётся
`succeeded`, в «Истории оплат» он помечен как возвращённый.

- Вернуть можно только платёж, которым заканчивается оплаченный срок: иначе
  после снятия его месяцев между платежами остался бы провал. Несколько — с
  последнего к первому (`NOT_LATEST`).
- Демо- и песочничные платежи (`demo-…`, `sandbox-…`) не возвращаются
  (`NOT_REFUNDABLE`), как и неоплаченные и уже возвращённые.
- Возврат частичный не поддерживается. Тело ответа банка в коллекции Точки не
  описано, поэтому отказом считаем ошибку HTTP или явный `isRefund: false`.
- Если банк вернул деньги, а запись в базе не удалась, в лог пишется
  `billing.refund_unrecorded`: нужно разобрать руками.
- Экрана для администратора пока нет, процедура вызывается через API.
